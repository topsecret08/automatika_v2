# ТЗ. Выносной HMI на ESP32-S3-Touch-LCD-7 с связьью по RS485 с контроллером Automatika

Версия: 1.0
Дата: 2026-11-24
Статус: проект

---

## 1. Назначение

Создать выносной сенсорный пульт управления (HMI) на базе платы **Waveshare ESP32-S3-Touch-LCD-7** (800×480, RGB, GT911, CH422G). Пульт подключается к существующему контроллеру **Automatika V0.9.6** по интерфейсу **RS485 (2-проводной, half-duplex)**.

Пульт является **только панелью displaying/управления**. Вся логика безопасности, PID, управление нагревом 220 В, клапанами и приводами остаётся на контроллере.

### 1.1. Цели

1. Получить 7-дюймовый дисплей без переноса основной прошивки на RGB-плату.
2. Не изменять распиновку датчиков/исполнителей контроллера.
3. Сохранить локальный LCD, PWA, Android и MQTT-каналы контроллера без изменений.
4. Обеспечить диагностируемую, помехоустойчивую связь в условиях перегонной установки.

### 1.2. Не цели

- Перенос прошивки Automatika на Waveshare.
- Передача ШИМ/нагрева по RS485 в реальном времени.
- Использование пульта как аварийной защиты вместо E-STOP.

## 2. Архитектура

```
┌──────────────────────────────┐        RS485 A/B + GND        ┌──────────────────────────────┐
│  HMI: ESP32-S3-Touch-LCD-7   │◄─────────────────────────────►│  Контроллер Automatika       │
│  - LVGL 8.3, 800×480         │      115200 8N1, master       │  - ESP32-S3-N16R8             │
│  - GT911, CH422G              │      запрос-ответ 1 Гц        │  - датчики, PID, safety       │
│  - UART2 RS485 (GPIO15/16)   │                              │  - UART2 + transceiver        │
│  - своя прошивка / свой OTA  │                              │  - своя прошивка / OTA        │
└──────────────────────────────┘                              └──────────────────────────────┘
```

**Мастер шины — HMI.** Контроллер отвечает только на запросы. Это исключает коллизии при half-duplex.

## 3. Аппаратная часть

### 3.1. Сторона HMI (Waveshare)

| Ресурс | Использование |
|---|---|
| ESP32-S3-N16R8 | MCU, 16 MB Flash, 8 MB PSRAM |
| RGB 800×480 | LVGL 8.3, framebuffer в PSRAM |
| GT911 | тач, I²C GPIO8/9, IRQ GPIO4, RST через CH422G EXIO1 |
| CH422G | подсветка EXIO2, RST LCD EXIO3, RST тача EXIO1, CS TF EXIO4 |
| UART2 RS485 | GPIO15 = RS485_TXD, GPIO16 = RS485_RXD |
| Направление | автоматическое (встроенная схема платы), отдельный DE не нужен |
| Питание | Type-C 5 В, не менее 450 мА |

Базовый проект прошивки HMI: `waveshareteam/ESP32-S3-Touch-LCD-7/examples/ESP-IDF/08_lvgl_v8_demo`.

### 3.2. Сторона контроллера

| Ресурс | Требование |
|---|---|
| UART | **UART2**. UART1 зарезервирован под внешний регулятор (`REG_UART_NUM = 1`), UART0 — логи/прошивка |
| TX/RX | задаются в `main/config.h`, рекомендуется `TX=GPIO39`, `RX=GPIO1` (проверить по реальной плате) |
| DE/RE | отдельный GPIO, рекомендуется `GPIO38` (в конфиге `RS485_DE_GPIO`) |
| Трансивер | 3.3 В, например MAX3485/SP3485, с fail-safe bias |
| Лимиты | 10 запросов/с, burst 20 — переиспользовать идеологию `API_RATE_LIMIT_PER_S` |

### 3.3. Кабель

- Экранированная витая пара A/B + отдельный GND.
- Терминирующие резисторы 120 Ом **на обоих концах**.
- Fail-safe смещение (bias) — в одной точке, предпочтительно на контроллере.
- При длине >5 м или рядом с силовыми кабелями — гальваническая развязка и отдельный изолированный DC/DC.
- Экран заземлять в одной точке у контроллера.

## 4. Протокол обмена

### 4.1. Физический уровень

| Параметр | Значение |
|---|---|
| Скорость | **115200 бод** (рабочая; fallback 57600 при помехах) |
| Формат | 8N1 |
| Режим | half-duplex, 2 провода |
| Master | HMI |
| Период опроса | **500 мс (2 Гц)** |
| Таймаут ответа | **100 мс** (150 мс при 2 повторах почти не оставляет времени до 500 мс) |
| Повторы | 2, сразу после таймаута |
| Межкадровый интервал | ≥ 2 мс после передачи перед приёмом |

При 115200 и 500 мс поток ~504 Б/с = **4.4 %** линии. При 57600 — ~8.8 %.
Если контроллер отдаёт телеметрию только 1 Гц, опрос 2 Гц вернёт те же
данные дважды: нужен снапшот на каждый `POLL` либо генерация телеметрии 2 Гц.
Потеря 3 опросов подряд = 1.5 с → `link=false`, но таймаут 100 мс всё ещё
укладывается в цикл 500 мс даже при двух повторах.

### 4.2. Формат кадра

```
| AA | 55 | LEN_LO | LEN_HI | SEQ_LO | SEQ_HI | NODE | TYPE | PAYLOAD[LEN] | CRC_LO | CRC_HI |
```

| Поле | Размер | Описание |
|---|---:|---|
| SOF | 2 | `AA 55` |
| LEN | 2 | длина PAYLOAD, little-endian, ≤ 512 |
| SEQ | 2 | номер кадра отправителя, инкремент |
| NODE | 1 | `0x10` — контроллер, `0x20` — HMI |
| TYPE | 1 | тип сообщения |
| PAYLOAD | LEN | JSON UTF-8 без перевода строки |
| CRC | 2 | CRC-16/CCITT-FALSE, poly `0x1021`, init `0xFFFF`, считается по байтам от LEN до конца PAYLOAD |

### 4.3. Типы сообщений

| TYPE | Направление | Назначение |
|---:|---|---|
| `0x01` | HMI → контроллер | `POLL` — запрос телеметрии |
| `0x81` | контроллер → HMI | `TELEMETRY` — ответ |
| `0x02` | HMI → контроллер | `CMD` — команда |
| `0x82` | контроллер → HMI | `ACK` — результат команды |
| `0x03` | HMI → контроллер | `GET_CONFIG` |
| `0x83` | контроллер → HMI | `CONFIG` |
| `0x04` | HMI → контроллер | `PING` |
| `0x84` | контроллер → HMI | `PONG` |

Контроллер **не отправляет** ничего без запроса. Все события попадают в поле `ev` кадра `TELEMETRY`.

### 4.4. TELEMETRY (payload)

```json
{
  "v":"V0.9.6",
  "tc":78.40,"ts":77.90,"p":42.0,"m":12.5,
  "sa":1,"es":0,"lv":68,"r":1,"stg":2,
  "run":1,"pause":0,"heads":150,"body":820,"tails":0,
  "elapsed":3120,"frac":"body",
  "baro":1012.4,"flow":2.10,"sd":1,"db":1,"heap":182344,
  "ev":[{"type":0,"msg":"...","ts":1731500000}]
}
```

Соответствие полей:

| Поле | Источник в контроллере |
|---|---|
| `tc`, `ts`, `p`, `m`, `r`, `stg` | `state_snapshot()` / `GET /api/state` |
| `sa`, `es` | `ctrl_safety_ok()`, `estop_is_pressed()` |
| `lv` | `level_get_percent()` |
| `heads/body/tails/elapsed/pause` | `process_state_t` |
| `frac`, `baro`, `flow` | `GET /api/env` |
| `sd`, `db`, `heap` | `GET /api/health` |
| `ev` | кольцевой журнал, только новые записи с момента последнего POLL |

Размер payload ≤ 512 байт. Если事件 не помещаются — отправить только последние 3."

### 4.5. CMD (payload)

```json
{"cmd":"start"}
{"cmd":"pause"}
{"cmd":"stop"}
{"cmd":"power","power":35}
{"cmd":"mode_auto"}
{"cmd":"safety_reset"}
{"cmd":"stage_next"}
{"cmd":"param","name":"open_time","value":1.5}
{"cmd":"profile_set","name":"default"}
{"cmd":"selection_param","name":"heads_timer","value":3600}
```

Разрешённый список команд — белый список. Любой неизвестный `cmd` → `ACK{"ok":false,"err":"unknown_cmd"}`.

### 4.6. ACK (payload)

```json
{"ok":true,"seq":1234}
{"ok":false,"seq":1234,"err":"estop_active"}
```

`seq` — номер кадра `CMD`, который подтверждается.

### 4.7. Поведение при ошибках

- Неверный CRC — кадр игнорируется, счётчик `rs485_crc_err++`.
- Неверный SEQ для `CMD` — игнорируется (защита от повтора после reconnect).
- Нет ответа на `POLL` 3 цикла подряд — HMI показывает «НЕТ СВЯЗИ», не меняет режимы.
- Команды во время `estop=1` или `safety=0` отклоняются, кроме `safety_reset` по правилам `POST /api/safety`.
- Контроллер при потере链接 продолжает работу по последним уставкам.

## 5. Требования к прошивке HMI

### 5.1. Стек

| Компонент | Версия |
|---|---|
| ESP-IDF | ≥ 5.2 (совместимо с проектом) |
| LVGL | 8.3.11 — та же major, что у контроллера |
| База | `08_lvgl_v8_demo` Waveshare |
| Доп. компоненты | `espressif/esp_lcd_touch_gt911`, `esp_lvgl_adapter` (опционально) |

### 5.2. Экраны

1. **Главный** — куб/царга, мощность, давление, расход, уровень, E-STOP, safety, статус связи, фаза/этап.
2. **Управление** — Start/Pause/Stop, мощность 0…100 %,.auto режим, сброс аварии с подтверждением.
3. **Отбор** — HEADS/BODY/TAILS, таймеры, ручной перевод этапа.
4. **Профили** — список, выбор, редактирование базовых параметров.
5. **Настройки связи** — скорость, node id, таймаут, проверка `PING`.
6. **Журнал** — последние события из `ev`.
7. **Диагностика** — crc-ошибки, ретраи, last response time, версия прошивки HMI.

### 5.3. Реализация

- LVGL-задача и блокировки — по образцу демо Waveshare.
- Draw buffer 800×480 в PSRAM, 2 кадра + bounce buffer.
- Размеры виджетов и шрифты адаптировать под 800×480 (в Automatika много фиксированных 48×320 значений).
- RS485-стенд: задача `rs485_hmi_task`, watchdog `wd_register`, приоритет ниже safety/mode.
- Настройки链接 хранить в NVS HMI.
- Отдельный OTA для HMI (не путать с OTA контроллера).

### 5.4. Запреты

- Не хранить логикуafety/PID на HMI.
- Не слать команды чаще 4/с.
- Не блокировать UI ожиданием ответа дольше 200 мс.
- Не хардкодить API-ключи/пароли в прошивке.

## 6. Требования к прошивке контроллера

### 6.1. Изменения

1. Добавить `main/rs485/rs485_hmi.c/.h`:
   - UART2 + DE/RE GPIO;
   - приём кадра по LEN/SEQ/CRC;
   - dispetcher команд;
   - сериализатор телеметрии в cJSON.
2. Добавить в `main/config.h`:
   - `RS485_UART_NUM 2`
   - `RS485_TX_GPIO`, `RS485_RX_GPIO`, `RS485_DE_GPIO`
   - `RS485_BAUD 115200`
   - `RS485_POLL_MIN_MS 500`
   - `RS485_REPLY_TIMEOUT_MS 100`
   - `RS485_MAX_RETRIES 2`
   - `RS485_TX_GAP_US 2000`
3. Добавить в `main/CMakeLists.txt` `REQUIRES`: `driver`, `cJSON` уже есть.
4. Зарегистрировать задачу в `app_main()` с `wd_register("rs485_hmi", ...)`.
5. **Не дублировать** логику из `web_api.c`: команды должны вызывать те же функции ядра (`core/control_*`, `safety_gate`, `ctrl_heater_*`, `ctrl_safety_*`), что и REST/MQTT.

### 6.2. Совместимость

- Local LCD 480×320, PWA `/`, Android и MQTT продолжают работать.
- OTA-раздел, partitions.csv и NVS-схема не меняются.
- При отсутствии RS485-модуля прошивка собирается и работает как раньше.

## 7. Безопасность

| Требование | Реализация |
|---|---|
| E-STOP | механический разрыв фазы + GPIO7 на контроллере. HMI только отображает `es` |
| Связь | не является путём аварийного останова |
| Команды | проходят общий `safety_gate`, те же проверки, что у REST |
| Стоп/сброс аварии | подтверждение на экране HMI |
| Нет связи | HMI показывает «НЕТ СВЯЗИ», контроллер сохраняет последнее безопасное состояние |
| Повтор кадра | SEQ + белый список команд, ACK с seq |
| Доступ | физический кабель внутри корпуса; при выводе наружу — опциональный HMAC в PAYLOAD |

## 8. Тестирование

### 8.1. Протокол (host/unit)

- CRC на корректном кадре.
-CRC на искажённом кадре.
- Укороченный/переполненный LEN.
- Неверный NODE/TYPE.
- Дубли SEQ.
- Таймаут и 2 повтора.

### 8.2. Стенд

1. Кабель 10 м рядом с силовым кабелем и SSR — 24 ч, счётчик `rs485_crc_err` = 0.
2. Нажать E-STOP — `es=1` на HMI в течение ≤1 с, нагрев снят.
3. Оборвать A/B — HMI показывает offline ≤3 с, контроллер продолжает процесс.
4. Восстановить связь — telemetry возобновляется без перезапуска контроллера.
5. Одновременно工作的 PWA, local LCD и HMI — без деградации.
6. `POST /api/start` и `CMD start` дают одинаковый результат safety-проверок.

### 8.3. Приёмка

| Критерий | Значение |
|---|---|
| Задержка телеметрии | ≤ 1.5 с |
| CRC-ошибки | < 1×10⁻⁶ кадров на тестовом стенде |
| Отображение E-STOP | ≤ 1 с |
| Потеря связи | не изменяет состояние контроллера |
| Сборка | `idf.py build` для обоих проектов |
| Оба OTA | сохраняются рабочими |

## 10. Риски

| Риск | Митигация |
|---|---|
| Помехи от SSR/нагревателя | экранированная пара, 120 Ом, гальваника, 115200 бод (fallback 57600) |
| Коллизии в half-duplex | master-only HMI,应答 только по запросу |
| Дубли команд после reconnect | SEQ, ACK seq, белый список |
| Путаница прошивок HMI и контроллера | разные репозитории/ветки и разные OTA-пути |
| Ошибка в GPIO DE | проверка осциллографом до подключения силовой части |
| Несовместимость LVGL 8/9 | HMI остаётся на LVGL 8.3.11 |
