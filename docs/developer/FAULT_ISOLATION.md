# Контракт изоляции отказов и границы валидации

Документ фиксирует, что критично для управления нагревом, что не должно
влиять на контур, и какие проверки пока не автоматизированы.

## 1. Критический контур (ядро 1)

- `estop` — аппаратная кнопка, ISR + опрос; отказ инициализации блокирует
  нагрев и виден в API.
- `safety` — E-STOP, перегрев, давление, датчики, проток, уровень,
  пролив; защёлка аварии.
- `mode` — рабочий режим и уставки.
- `ctrl_heater` — единственный путь DAC/UART/PWM; проверяет E-STOP,
  safety, уровень, обязательный датчик уровня и запущенный процесс/сервис.
- `level` — обязательный датчик при `LEVEL_SENSOR_REQUIRED=1`.
- `regulator_driver` — инициализация и аварийное обнуление выходов.

Отказ любого компонента этого контура должен приводить к нулевому выходу
и/или аварии, а не к продолжению нагрева.

## 2. Некритический контур

- Web/PWA, MQTT, Telegram, Samovar, Brewfather, календарь.
- Lua-скрипты (sandbox, лимит памяти/инструкций).
- AI-модули (`anomaly`, `tinyml`, `autolearn`, `predictive`).
- Графики, экспорт, уведомления.

Их падение не должно останавливать safety/mode/heater. Команды управления
из этих интерфейсов проходят через `safety_gate_apply()` и общий
`ctrl_heater`, а не пишут в DAC/UART/PWM напрямую.

## 3. Что уже есть

- Watchdog с критическими задачами (`estop`, `safety`, `scale`, `mode`):
  зависание критической задачи приводит к перезагрузке.
- Защёлка E-STOP, низкого уровня и `LEVEL_SENSOR_FAIL`.
- Запрет OTA при работающем процессе и единый `ota_guard`.
- Отдельные задачи web/telegram/mqtt/lua; сетевые ошибки не блокируют
  safety.
- SQLite-запись и `verify_trace` не входят в путь управления.

## 4. Чего пока нет

| Область | Состояние |
|---|---|
| HIL-стенд / симулятор процесса | нет; сценарии выполняются на реальной плате |
| Fault injection (обрыв I2C, зависание задачи, переполнение очереди) | нет автоматического набора |
| Эталонные трассы для AI | нет; AI-модули не используются как источник команд нагрева |
| Метрики `verify_trace` (MTBF, error rate, max latency) | нет автоматического анализа |
| Replay-харнесс регрессии | есть ручной replay, нет CI-прогона |
| Формальный контракт падения web/mqtt | зафиксирован в этом документе, но без fault-injection тестов |

Эти пункты остаются задачами следующего этапа; они не маскируются
«зелёной» сборкой.

## 5. Правило для новых модулей

Новый модуль, который может влиять на нагрев, обязан:

1. проходить через `safety_gate_apply()` / `ctrl_heater_*`;
2. не обращаться к LEDC/DAC/UART напрямую;
3. иметь отказ в сторону нулевого выхода;
4. не блокировать safety-задачу;
5. быть покрыт host-тестом чистой логики или стендовой процедурой.
