# Архитектура

Обзор прошивки Automatika v2.9.3 для ESP32-S3 (ESP-IDF 5.3.2). Документ
описывает то, что реально собрано из `main/`, а не исходное ТЗ.

## 1. Слои

```
┌──────────────────────────────────────────────────────────────┐
│ UI (LVGL, touch, физические кнопки)   Web/PWA   Telegram/MQTT│
├──────────────────────────────────────────────────────────────┤
│ Режимы (modes/)   Сессии   Профили   Lua-скрипты   OTA        │
├──────────────────────────────────────────────────────────────┤
│ Регулирование (control/): heater, PID, safety, valves, dose,  │
│ reflux, fractions, autotune                                   │
├──────────────────────────────────────────────────────────────┤
│ Состояние и события (core/): state, events, health, flags,    │
│ config, NVS-миграции, backup, i18n                            │
├──────────────────────────────────────────────────────────────┤
│ HAL (hal/): I2C, 1-Wire, ADS1115, MCP4725, PCA9685, Grove SSR,│
│ BMP280, flow, HX711, LCD/touch, SD                            │
├──────────────────────────────────────────────────────────────┤
│ ESP-IDF: FreeRTOS, lwIP, esp_http_server, mbedTLS, littlefs   │
└──────────────────────────────────────────────────────────────┘
```

Правило зависимостей: верхние слои знают о нижних, не наоборот. `hal/`
не вызывает `control/`; `control/` не знает про HTTP. Веб-слой читает
`state_get()` и вызывает публичные функции управления.

## 2. Ядра и задачи

`core/core_pinning.h`:

- **Core 0** — сеть и «тяжёлое»: Wi-Fi, HTTP/HTTPS, WebSocket-отправка,
  MQTT, Telegram, OTA, БД, предиктор.
- **Core 1** — реальное время: E-STOP, safety, режим, UI, весы, нагреватель,
  дозирование.

Ключевые задачи:

| Задача | Ядро | Приоритет | Стек | Назначение |
|---|---:|---:|---:|---|
| `estop` | 1 | 20 | 2048 | опрос E-STOP, антидребезг 50 мс |
| `safety` | 1 | 19 | 4096 | проверки уровня/потока/давления/температур |
| `mode` | 1 | 10 | 8192 | конечный автомат процесса |
| `ui` | 1 | 8 | 8192 | LVGL |
| `ws_tel` | 1 | 8 | 4096 | сборка кадра телеметрии раз в секунду |
| `scale` | 1 | 6 | 4096 | HX711 |
| `heater` | 1 | 6 | 3072 | применение мощности, trend guard |
| `web` | 0 | 5 | 8192 | HTTP :80 + HTTPS :443 |
| `tg_bot` | 0 | 3 | 8192 | Telegram getUpdates, команды, inline-кнопки |
| `wifi` | 0 | 23 | 4096 | provisioning/STA |
| `doser` | 0 | 4 | 4096 | шаговый дозатор |
| `dblog`, `events` | 0/1 | 3 | 3072–4096 | журналы |
| `ota_mgr` | 0 | 3 | 4096 | OTA |

`ws_tel` живёт на Core 1, но отправка кадров идёт через
`httpd_ws_send_frame_async()`, поэтому сетевой ввод-вывод остаётся на
Core 0 (в контексте HTTP-сервера). Это осознанный компромисс: кадр
собирается рядом с состоянием, а сокет не блокирует реальное время.

## 3. Поток данных

```
DS18B20 ─┐
BMP280  ─┤
ADS1115 ─┼─> hal_* ─> state ─> control ─> actuators
YF-S201 ─┤             │                   (MCP4725, PCA9685, Grove SSR,
HX711   ─┘             │                    A4988)
                       ├─> events_log() ─> ring buffer / NVS / SD
                       ├─> health_check ─> /api/health
                       └─> ws_telemetry ─> /ws/telemetry
```

`state` — единственный источник истины для UI и API. Он обновляется
задачами датчиков и регулирования; HTTP-обработчики только читают его
(кроме команд, которые меняют уставки через функции control).

## 4. Безопасность

Три независимых уровня:

1. **Аппаратный** — E-STOP механически разрывает фазу 220 В. Прошивка
   не может это отменить.
2. **Задачный** — `estop` (prio 20) и `safety` (prio 19) вытесняют
   управление. `ctrl_heater_set_percent()` в начале проверяет
   `estop_is_pressed()` и `ctrl_safety_ok()` и обнуляет мощность.
3. **Программный** — `health_check_healthy()` не даёт подтвердить OTA и
   переводит `/api/health` в `fail` при `estop active`, `safety fault`,
   нехватке внутренней RAM (< 40 КБ) или зависшей задаче.

Пороговые значения — в `main/config.h`: `SAFE_MAX_PRESSURE = 3.0`,
`SAFE_MAX_CUBE_T = 130 °C`, `SAFE_MAX_COLUMN_T = 105 °C`,
`SAFE_MIN_FLOW = 0.5 л/мин`.

## 5. Веб-слой и PWA

- Один набор обработчиков регистрируется на двух серверах: HTTP
  (`s_srv`, порт 80) и HTTPS (`s_https`, порт 443).
- Статика PWA встроена в приложение (`EMBED_FILES`) и одновременно
  собирается в образ littlefs `assets.bin`. Встроенная копия —
  авторитетная: она работает без файловой системы и всегда соответствует
  прошивке. Образ — канонический источник и артефакт прошивки.
- Статический fallback (`/*`) отдаёт только файлы из `/lfs/www`. Корень
  `/lfs` намеренно не отдаётся: там лежат профили, скрипты, резервные
  копии и ключи, доступ к которым должен идти через API с `X-API-Key`.
- HTTPS-сервер (`web/https_server.c`) при первом старте генерирует
  EC P-256 самоподписанный сертификат, сохраняет `cert.pem`/`key.pem`
  в `/lfs` и поднимает `httpd_ssl_start`.
- `web/ws_telemetry.c` хранит пары `{fd, srv}`: HTTP и HTTPS — разные
  `httpd_handle_t`, и отправлять кадр «через другой» сервер нельзя.
- HTTP→HTTPS редирект выключен по умолчанию: HTTP-клиенты и API работают
  без установленного сертификата. При `WEB_HTTPS_REDIRECT=1` статика на
  порту 80 отвечает `301`, но `/api/*` и `/cert.pem` остаются доступны
  по HTTP.

Подробности API — [API.md](API.md), установка PWA —
[../user/PWA_INSTALL.md](../user/PWA_INSTALL.md).

## 6. Память и разделы

`partitions.csv` (16 МБ flash):

| Раздел | Тип | Смещение | Размер |
|---|---|---|---|
| `nvs` | data/nvs | `0x9000` | 24 КБ |
| `otadata` | data/ota | `0xF000` | 8 КБ |
| `phy_init` | data/phy | `0x11000` | 4 КБ |
| `factory` | app/factory | `0x20000` | 3 МиБ |
| `ota_0` | app/ota_0 | `0x320000` | 3 МиБ |
| `ota_1` | app/ota_1 | `0x620000` | 3 МиБ |
| `assets` | data/littlefs | `0x920000` | 1 МиБ |
| `storage` | data/spiffs | `0xA20000` | 5.875 МиБ |

`factory` — страховочный образ; `otadata` переключает `ota_0`/`ota_1`.
Все app-слоты по 3 МиБ, потому что текущий образ ~2.37 МиБ и в 2 МиБ не
влезает. Это отличие от исходного ТЗ (там было 2 МиБ); альтернатива —
урезать функциональность, что неприемлемо. Littlefs-раздел называется
`assets` исторически; менять метку нельзя без правки
`LFS_PARTITION_LABEL` и потери пользовательских данных.

PSRAM (8 МБ) используется для буферов LCD, кэша и SQLite; внутренняя RAM
контролируется health-check.

## 7. Загрузка

`app_main()`:

1. NVS, storage, littlefs, профили.
2. HAL: 1-Wire, барометр, давление, поток, DAC, реле, LCD, touch.
3. Регулирование и безопасность, сессии, рефлюкс.
4. БД, кэш, предиктор, аномалии, TinyML, UI-preloader.
5. OTA, Telegram, MQTT, Samovar.
6. Wi-Fi provisioning (SoftAP + mDNS).
7. health, UI, меню, диалог восстановления сессии.
8. Задачи Core 0 и Core 1.

Если Wi-Fi не поднят, `web_start()` завершает задачу и сервер не
стартует — устройство остаётся управляемым с локального экрана.

## 8. Отклонения от исходного ТЗ

| ТЗ | Реализовано | Причина |
|---|---|---|
| OTA-слот 2 МиБ | 3 МиБ | образ ~2.58 МиБ не влезает |
| `littlefs` раздел | `assets` + `/lfs` | метка прошита в конфигурации |
| HTTP→HTTPS всегда | опционально, по умолчанию выкл. | статика на :80 редиректится, API и `/cert.pem` остаются |
| E-STOP на GPIO 18 | GPIO 27 | 18 занят LCD MOSI |
| ошибки E01–E08 | `health.level/reason` + события | коды не были реализованы |
| команды Telegram | polling-бот: `/status`, `/run`, `/stop`, `/power`, `/log` | команды только из настроенного chat_id |
| загрузка профиля из Telegram | только список профилей | смена режима/уставок остаётся в вебе |
| push через Web Push | SW готов, серверной части нет | нет VAPID; уведомления в Telegram |
| `/api/sensors/*` | `/api/state`, `/api/env` | таких обработчиков нет |
| ACS712 | ADS1115 A2 (пролив), A3 (пары) | в коде нет ACS712 |

Эти отклонения важны для сопровождения: документация и интерфейс не
должны обещать несуществующее.

## 9. Соглашения

- Комментарии — по-русски, кратко объясняют «почему», а не «что».
- Публичные функции модуля — в `.h`, статические — в `.c`.
- Ошибки логируются через `events_log()` и `ESP_LOGx`.
- Новые задачи регистрируются в watchdog (`wd_register`) и кормят его.
- Секреты не попадают в репозиторий и в `sdkconfig.defaults`.
