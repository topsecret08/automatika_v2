# Процедуры тестирования

Приёмо-сдаточные и периодические проверки. Выполняются на собранном
устройстве с прошивкой V0.5 alfa. Для команд нужен API-ключ; подставьте его
в `X-API-Key`.

Обозначения:

- `HOST` — `automatika.local` или IP устройства;
- `KEY` — API-ключ (генерируется в Настройках, в коде значения по умолчанию нет);
- все `POST` — с `-H "Content-Type: application/json"`.

## 0. Подготовка

```bash
export HOST=automatika.local
export KEY=<ваш-ключ>
curl -s http://$HOST/api/health
```

Ожидается `"level":"ok"` или `"degraded"` (без SD-карты/части датчиков).
`"level":"fail"` — дальнейшие тесты не имеют смысла, сначала устраните причину.

## 1. Загрузка и сеть

| Проверка | Действие | Критерий |
|---|---|---|
| Загрузка | открыть монитор 115200 бод | нет `abort()`, нет циклического reset |
| Wi-Fi | `GET /api/health` | `wifi_rssi` от −30 до −85 дБм |
| HTTP | `curl -I http://$HOST/` | `200 OK`, заголовки безопасности |
| HTTPS | `curl -k -I https://$HOST/` | `200 OK` |
| PWA manifest | `curl -s http://$HOST/manifest.json` | валидный JSON, иконки 192/512 |
| Service Worker | `curl -sI http://$HOST/sw.js` | `Service-Worker-Allowed: /` |
| Сертификат | `curl -s http://$HOST/cert.pem` | PEM, `BEGIN CERTIFICATE` |
| Приватный ключ | `curl -s -o /dev/null -w "%{http_code}" http://$HOST/key.pem` | `404` |

## 2. Датчики температуры (DS18B20)

1. Комнатная температура, датчики в воздухе.
2. `GET /api/env` и `GET /api/health` → `sensors`.
3. Критерии:
   - `sensors` = 2 (или 1, если используется один датчик);
   - показания 18–30 °C, расхождение между датчиками ≤ 1 °C;
   - нет `-127` и `85`.
4. Опустить датчик в воду 40 °C: показания должны вырасти и стабилизироваться
   за 10–20 с.

## 3. Давление и барометр (BMP280 + ADS1115)

1. `GET /api/env`.
2. `baro.present` = 1; `baro.hpa` в диапазоне 950–1050 (зависит от высоты).
3. `baro.boiling_c` — температура кипения с поправкой на давление
   (около 100 °C на уровне моря).
4. `column.kpa` — не должна «скакать» больше чем на 5 % в покое.

## 4. Проток охлаждения (YF-S201)

1. Без потока: `flow.lpm` ≈ 0, `flow.ok` = 0.
2. Подать воду 1–5 л/мин: `flow.lpm` в пределах ±10 % от эталона,
   `flow.ok` = 1.
3. Превышение порога `SAFE_MIN_FLOW` (0.5 л/мин) должно сниматься
   при возобновлении потока.
4. Если показания «дребезжат» — проверить экранирование и подтяжку линии
   GPIO 2.

## 5. Нагреватель и SSR (сервисный режим)

> Тест выполнять с заполненным кубом или с подключённой эквивалентной
> нагрузкой. Не включайте нагрев «в воздух» на длительное время.

1. Включить сервисный режим:
   `POST /api/diag/service {"enabled":true}`.
2. `POST /api/diag/actuators {"actuator":"heater","action":"on","pct":20,"seconds":5}`.
3. Критерии:
   - слышен щелчок SSR;
   - ток потребления растёт (токовые клещи);
   - `GET /api/state` → `power` ≈ 20;
   - через 5 с нагрев автоматически выключается.
4. `POST /api/diag/actuators {"actuator":"heater","action":"off"}` —
   `power` = 0.
5. Выключить сервисный режим.

## 6. Клапаны и реле (PCA9685 / Grove SSR)

1. `POST /api/diag/actuators {"actuator":"valve","action":"open"}` —
   клапан открывается, слышен щелчок/движение сервопривода.
2. `POST /api/diag/actuators {"actuator":"valve","action":"close"}` —
   закрывается.
3. Реле: `{"actuator":"relay","action":"set","ch":0,"state":1}` включает
   канал 0 (охлаждение), `state:0` — выключает. Проверить все 4 канала.
4. Убедиться, что при `E-STOP` клапаны и реле переводятся в безопасное
   состояние (нагрев — выключен).

## 7. Дозирующий насос (A4988)

1. Заполнить мерный цилиндр водой.
2. `POST /api/dose {"volume_ml":10,"rate_mlmin":60}`.
3. Измерить фактический объём.
4. Критерий: ±3 % (9.7–10.3 мл). Иначе — калибровка `steps_per_ml`
   (см. SERVICE_MANUAL.md, §5.1), затем повтор.
5. Проверить отсутствие пропусков шагов: 10 циклов по 10 мл, суммарно
   100 ± 3 мл.

## 8. Аварийная цепь

| Шаг | Ожидание |
|---|---|
| Нажать E-STOP при работающем нагреве | нагрев снят немедленно, `GET /api/health` → `estop:1`, `level:"fail"` |
| Отпустить E-STOP | `estop:0`, но процесс не возобновляется сам |
| `POST /api/safety` | сброс аварии, `safety:1` |
| Разрыв цепи датчика уровня | safety срабатывает, нагрев выключается |
| Отключение потока воды | safety по `SAFE_MIN_FLOW` |

**E-STOP проверяется физически:** разрыв фазы 220 В должен происходить
независимо от прошивки. Программная реакция — дополнение, а не замена.

## 9. Журнал событий

1. `GET /api/events?limit=50`.
2. Критерии:
   - события содержат метку времени и тип;
   - действия пользователя (`EVENT_USER_ACTION`) фиксируются;
   - аварии (`EVENT_EMERGENCY`) не теряются при перезагрузке в пределах
     кольцевого буфера (200 записей).
3. `GET /api/events` без ключа → `401`.

## 10. OTA и откат

1. `GET /api/ota` — текущий статус, нет активного обновления.
2. Проверить размер образа: не больше размера OTA-слота (3 МиБ).
3. Запустить обновление на тестовый образ:
   `POST /api/ota/url {"url":"https://<host>/automatika_v2.bin"}`.
4. Дождаться перезагрузки; `GET /api/health` → новая версия.
5. Проверить, что при неработоспособном образе происходит откат
   (имитируется тестовым образом, который не проходит health-check).
6. `POST /api/ota/confirm` — ручное подтверждение (если авто-подтверждение
   отключено).

## 11. PWA на телефоне

1. Открыть `https://$HOST` в Chrome (Android) или Safari (iPhone).
2. Принять самоподписанный сертификат (или установить `cert.pem`
   как доверенный — см. [PWA_INSTALL.md](../user/PWA_INSTALL.md)).
3. Chrome: появится кнопка «Установить»; Safari: «Поделиться» →
   «На экран "Домой"».
4. После установки:
   - приложение запускается в standalone-режиме;
   - иконка и название корректны;
   - ярлыки «Дашборд», «Журнал», «Настройки» работают;
   - при отключении Wi-Fi показывается offline-страница, затем
     восстанавливается соединение.
5. DevTools → Application → Cache Storage: кэш `automatika-v294-1`
   содержит оболочку.

## 12. Регрессия после прошивки

Минимальный набор при каждом обновлении:

1. `GET /api/health` → `ok`/`degraded`.
2. `GET /api/state` → разумные значения.
3. Wi-Fi + mDNS.
4. PWA открывается и обновляется (SW cached).
5. Нагрев 10 % / 5 с, затем off.
6. E-STOP.
7. `GET /api/events` содержит записи о старте и тесте.

Результаты фиксируйте в журнале устройства или в чек-листе партии.

## 13. P0: стендовая приёмка защит

Выполнять **без нагревательной нагрузки** (или с лампой/резистором на
безопасном напряжении). Для каждого пункта фиксируйте `GET /api/diag/safety`
до и после, показания мультиметра/осциллографа и запись в журнале.

### 13.1. E-STOP NC (GPIO 27)

| Состояние | Линия | `raw` | `pressed` | Выход |
|---|---|---:|---:|---|
| Норма (контакт замкнут на GND) | 0 | 0 | 0 | управляется |
| Нажата / контакт разомкнут | 1 | 1 | 1 | 0, процесс остановлен |
| Обрыв провода | 1 | 1 | 1 | 0 |
| КЗ провода на GND | 0 | 0 | 0 | **не обнаруживается** |

1. Замкнуть E-STOP на GND — устройство должно работать, `raw=0`.
2. Разомкнуть — в течение 100 мс выход 0, `pressed=1`, событие
   `E-STOP ACTIVE`.
3. Отсоединить провод — тот же результат, что при нажатии (обрыв).
4. Замкнуть провод на GND — аварии нет (ограничение схемы; для
   обнаружения КЗ нужен отдельный диагностический канал).

### 13.2. Обрыв датчиков температуры

1. Отключить DS18B20 при работающем процессе.
2. Ожидается: `t*_ok=0` в `/api/diag/safety`, переход в аварию или
   безопасное значение, мощность 0, процесс остановлен.
3. Подключить датчик обратно, сбросить аварию, убедиться, что показания
   восстанавливаются.

### 13.3. Низкий уровень и перелив

1. Опустить поплавок ниже порога — событие низкого уровня, нагрев 0.
2. Поднять до перелива — событие overflow, нагрев 0, клапан закрыт.

### 13.4. Пропадание протока

1. Перекрыть поток при работающем насосе/клапане.
2. Ожидается `flow.ok=0`, авария по протоку, мощность 0.
3. Открыть поток, сбросить аварию.

### 13.5. Отключение внешнего регулятора

1. Выбрать KVIC/РМВ-К/SEM/SSR и задать мощность.
2. Отключить питание или UART регулятора.
3. Ожидается `regulator_ready=0`, выход 0, ошибка в UI/PWA, для UART —
   повторная команда `P000` при восстановлении связи.
4. Проверить, что прошивка **не** переключается скрытно на DAC.

### 13.6. SSR/ШИМ (настраиваемый GPIO)

Задать в PWA/LCD/REST: `reg_gpio` (реально свободный вывод), частоту,
разрядность и полярность. Осциллографом на выбранном выводе:

| Уставка | Duty (10 бит) | Скважность |
|---:|---:|---:|
| 0 % | 0 | 0 % |
| 25 % | 256 | 25 % |
| 50 % | 512 | 50 % |
| 75 % | 768 | 75 % |
| 100 % | 1023 | 100 % |

Для инвертированного выхода 0 % — высокий уровень (неактивный для
активного низкого входа), 100 % — низкий.

Дополнительно:

1. Проверить, что при `reg_gpio=-1`, GPIO 22–25, 26–37 или занятом выводе
   `regulator_ready=false`, API/PWA/LCD показывают причину, выход 0.
2. Задать вручную 35 %, затем дать режиму вызвать 80 % — на выходе
   остаются 35 %.
3. Нажать «Авто» — выход становится 80 %.
4. E-STOP, авария, низкий уровень, «Стоп», смена регулятора — **немедленно** 0.
5. После перезагрузки — «Авто», выход 0, тип/GPIO/частота/полярность
   восстановлены из NVS.
6. Убедиться, что выбранная частота допустима для конкретного SSR;
   для AC SSR/zero-cross может потребоваться другой режим управления.
