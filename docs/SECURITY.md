# Модель угроз и меры защиты

Документ фиксирует, что именно защищено в V0.6 beta, а что остаётся
ответственностью монтажника и владельца устройства.

## 1. Границы доверия

| Интерфейс | Доступ | Защита |
|---|---|---|
| Локальный LCD/энкодер/кнопки | физический доступ | нет аутентификации (по определению) |
| HTTP/HTTPS API | локальная сеть | `X-API-Key`, HTTPS с самоподписанным сертификатом |
| PWA | браузер в локальной сети | тот же ключ, ключ хранится в `localStorage` |
| Telegram | интернет | секрет webhook + список chat id |
| MQTT | локальная сеть / брокер | логин/пароль брокера, если задан |
| Wi-Fi provisioning AP | физическая близость | PoP (security1) |
| OTA | локальная сеть / HTTPS URL | ключ API + TLS; подпись образа — см. п. 4 |

Устройство не выходит в интернет само, кроме SNTP и Telegram, если они
настроены. Порт проброса из интернета открывать не следует: для удалённого
доступа используйте VPN.

## 2. REST API: публичное и приватное

Публично (без ключа) доступен только `GET /api/health` — минимальный
набор признаков живости без секретов.

До генерации первого ключа (`api_key_set=0`) GET-чтение конфигурации и
телеметрии разрешено для первичной настройки. После провижининга ключа
**все** GET/POST, включая `/api/state`, `/api/control`, `/api/param`,
`/api/config`, `/api/events`, `/api/ota`, `/api/verify/*`, `/api/env`,
требуют `X-API-Key`. Исключение — `GET /api/health`.

WebSocket `/ws/telemetry` защищён короткоживущим токеном: PWA получает
его через `GET /api/ws-token` с `X-API-Key` и передаёт в
`Sec-WebSocket-Protocol` (`automatika,<token>`). Постоянный API-ключ в URL
не передаётся; до успешного handshake кадры не выдаются.

`POST /api/config/generate-key` при уже заданном ключе требует текущий
ключ. Ключ хранится в NVS и не попадает в логи. Смена ключа не стирает
остальную конфигурацию.

## 3. Wi-Fi provisioning и PoP

SoftAP `Automatika-Setup` доступен любому в радиусе, поэтому provisioning
работает в режиме **security1 с PoP** (`PROV_POP_SECRET 1`). Заводской PoP
(`PROV_POP_TEXT`) известен из исходников и не является секретом.

Требования для партии:

1. Задать уникальный `PROV_POP_TEXT` (>= 8 символов) перед сборкой.
2. Наносить PoP на этикетку устройства или выдавать вместе с ним.
3. Не оставлять AP включённым после настройки: при успешном подключении
   provisioning останавливается автоматически.
4. При компрометации PoP — перепрошить устройство с новым значением.

Остаточный риск: PoP передаётся по открытому радиоканалу внутри
защищённого handshake ESP provisioning; при физическом доступе атакующий
может перевести устройство в режим provisioning сбросом Wi-Fi.

## 4. OTA и подпись

- Транспорт: только `https://`, проверка сертификата через `esp_crt_bundle`
  (`CONFIG_ESP_HTTPS_OTA_ALLOW_HTTP=n`). `http://` запрещён.
- OTA блокируется единым `ota_guard_check()` для всех путей
  (`/api/ota`, `/api/ota/url`, `/api/ota/secure`, manager и secure):
  идёт другой OTA, процесс (`state_get()->is_running` или
  `session_is_running()`), E-STOP или авария.
- Anti-brick: `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`, подтверждение
  только после health-check.
- **Подпись образа пока выключена** (`OTA_SIGNED_ENABLED 0`): в репозитории
  нет ключей. Для production обязательно включить Secure Boot v2:
  сгенерировать ключ, включить `CONFIG_SECURE_BOOT` и
  `CONFIG_SECURE_SIGNED_APPS_RSA_SCHEME`, подписывать образ
  `espsecure.py sign_data`, затем выставить `OTA_SIGNED_ENABLED 1`.
  Без этого скомпрометированный HTTPS-сервер или ключ API позволяет
  установить произвольную прошивку.

## 5. Аппаратная безопасность

- E-STOP — нормально замкнутый контакт на GND, активный уровень высокий
  (нажатие или обрыв). Короткое замыкание линии на GND неотличимо от нормы;
  для его обнаружения нужен отдельный диагностический канал.
- E-STOP механически разрывает силовую цепь; GPIO 27 — только сигнал.
- UART-регуляторы подключаются через оптронную развязку; земли силовой и
  логической частей не соединяются.
- PWM GPIO (`REG_SSR_GPIO`) по умолчанию `-1`; задайте реально свободный
  вывод платы. У ESP32-S3 нет GPIO 22–25, а 26–37 обычно заняты flash/PSRAM;
  частота ШИМ подбирается под тип SSR.
- Finglai SSVR: только через преобразователь PWM → 0–5 В → CONT/COM.
  Не подавать 5 В на GPIO. Трёхфазная модель/нагрузка/ток/напряжение и
  развязка преобразователя должны быть сверены; это не замена однофазному
  SSR.
- Если E-STOP не инициализировался, `estop_is_pressed()` считается
  активным: нагрев заблокирован, причина видна в API.
- При E-STOP, аварии, низком уровне, «Стоп» и смене регулятора выход
  обнуляется для DAC, UART (`P000`) и PWM.

## 6. Остаточные риски

| Риск | Статус |
|---|---|
| Нет подписи OTA | известное ограничение, процедура в п. 4 |
| PoP по умолчанию общий | требует замены перед партией |
| Самоподписанный HTTPS | клиент должен принять сертификат вручную |
| Физический доступ к LCD | управление возможно без ключа |
| КЗ E-STOP на GND | не обнаруживается схемой |
| Lua | sandbox + лимит памяти 256 КБ + лимит инструкций/времени |
